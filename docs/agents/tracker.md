# Конфигурация трекера для агентов

Трекер проекта — GitHub Issues репозитория `TiltStable/frontend-project-386`.
Работа агента с трекером ведётся через `gh` CLI. Секретов в конфигурации нет:
авторизация — через окружение агента (`gh auth`).

## Точка входа агента

Перед началом работы прочитать в этом порядке:

1. [Карта решений — issue #1](https://github.com/TiltStable/frontend-project-386/issues/1):
   все принятые решения с ответами и обоснованиями.
2. [Спецификация — issue #2](https://github.com/TiltStable/frontend-project-386/issues/2)
   и каноничный файл [docs/spec.md](../spec.md): роли, пользовательские
   истории (US-1..US-5), правила окна и занятости, контракты API, границы
   тестирования.
3. [GLOSSARY.md](../../GLOSSARY.md) — словарь терминов, единые формулировки.
4. Открытые тикеты: `gh issue list --state open`.

## Конвенции тикетов

- Тикет реализации: цель, чеклист шагов (контракт → генерация → сервер →
  интерфейс → тесты), раздел «Зависимости» с номерами issues, ссылка на
  спецификацию (#2).
- Один тикет — одна вертикальная функция, проходящая все слои.
- Зависимости указываются явно («требует #N»); работа не начинается раньше
  закрытия зависимостей.
- Реализованный тикет закрывается комментарием со ссылкой на коммит (sha),
  закрывающий чеклист.
- Спецификация (#2) и карта решений (#1) — открытые reference-issues,
  не закрываются.
- Изменение API начинается с контракта (см. AGENTS.md → «Порядок правки
  контракта»), затем тикет обновляет чеклист реализации.

## Коммиты

- Conventional Commits обязательны (`feat:`, `fix:`, `docs:`, `test:`, `ci:`).
- Коммит реализации ссылается на тикет, который закрывает:
  `feat: запись на свободный слот (#12)`.
- Commits-msg хук (hk) отклоняет сообщения вне формата.

## Пример пройденного цикла

Тикеты #3–#8 (типы событий → слоты → бронирование → страница владельца →
e2e) прошли полный цикл: спецификация (#2) → зависимый граф → реализация
коммитами `(#N)` → закрытие с sha → мутационная проверка правила бронирования
записана в тикете (#5).
